## 3. Контекст проекта

Проект написан на C++20 и предназначен для Wiren Board ARM64 под Debian 11.

Основные свойства архитектуры:

- один экземпляр `mdvwb@N.service` обслуживает один физический порт RS-485;
- `deploy/mdvwb-run` выбирает runtime MDV или Modbus;
- общие семантические управления включают:
  - Power;
  - Mode;
  - FanSpeed;
  - SetTemperature;
  - Blinds;
  - Blocked;
- MQTT callbacks не должны непосредственно выполнять физические операции или менять runtime-состояние: они только ставят команды в очередь;
- физические операции и изменение состояния выполняются в одном runtime-потоке;
- ограниченные очереди являются намеренным архитектурным решением;
- Modbus-профиль `vrf_add_controller` использует логические адреса `1..63`;
- Modbus discovery и polling должны оставаться profile-driven;
- система должна продолжать поддерживать как MDV, так и Modbus;
- не следует вводить второй публичный systemd-сервис для того же физического порта.

Уже исправлено в исходной точке:

- при некорректном подтверждении записи `Power` Modbus-устройство переводится в offline;
- существует regression-тест этого поведения.

Не переделывать это исправление без необходимости и не допускать его регрессии.

# Задачи

## Задача 1. Безопасный rollback manager при повреждённом `buses.json`

### Проблема

При применении новой конфигурации manager пытается загрузить предыдущий `buses.json`.

Если старый файл отсутствует или повреждён, предыдущая конфигурация не распознаётся. При ошибке применения существующий rollback может построить пустую конфигурацию и синхронизировать систему с ней.

Это способно:

- удалить рабочие environment-файлы автобусов;
- отключить или остановить действующие сервисы;
- потерять фактическую рабочую топологию, которая до операции существовала в `/etc/default` и systemd.

### Требуемый результат

Перед любыми изменениями, относящимися к применению конфигурации, manager должен получить фактический снимок затрагиваемого runtime-состояния, не зависящий от возможности распарсить `buses.json`.

Снимок должен позволять восстановить:

- точное содержимое существовавших environment-файлов;
- отсутствие файлов, которых до операции не было;
- состояние `active` каждой затрагиваемой службы;
- состояние `enabled` каждой затрагиваемой службы;
- исходное содержимое или отсутствие `buses.json`.

При неуспешном apply:

- environment-файлы должны быть восстановлены;
- новые файлы должны быть удалены;
- удалённые файлы должны быть возвращены;
- службы должны быть приведены к прежним независимым состояниям `active` и `enabled`;
- активная служба после восстановления environment должна перечитать восстановленное содержимое;
- rollback не должен использовать пустой `BusesConfig` как замену фактическому старому состоянию;
- `buses.json.pending` и другие временные следы не должны оставаться после успешного rollback;
- при частично неуспешном rollback manager должен публиковать явный degraded/error status и не скрывать ошибку.

### Критерии приёмки

Добавить regression-тесты минимум для следующих случаев:

1. старый `buses.json` повреждён;
2. фактически существуют рабочие environment-файлы;
3. новая конфигурация частично применяется и затем падает;
4. после rollback все старые файлы восстановлены байт-в-байт;
5. новые файлы удалены;
6. проверены сочетания systemd-состояний:
   - active + enabled;
   - active + disabled;
   - inactive + enabled;
   - inactive + disabled;
7. подтверждено, что rollback не удаляет рабочую топологию;
8. отдельный тест проверяет диагностируемое поведение при ошибке самого rollback.

## Задача 2. Безопасные временные пути

### Проблема

В установочных и обслуживающих shell-скриптах используются предсказуемые пути на основе `$$`.

Известные области:

- `deploy/install-from-source.sh`;
- `deploy/offline-install.sh`;
- `deploy/mdvwb-setup`;
- связанные временные файлы, каталоги, staging и payload backup.

Предсказуемые пути создают риск symlink-атак, перезаписи чужих файлов и конфликтов параллельных запусков.

### Требуемый результат

Все временные файлы и каталоги должны создаваться безопасно:

- через `mktemp` или эквивалент;
- с ограничительными правами;
- с корректным cleanup;
- без следования заранее подготовленным симлинкам;
- без конфликтов между параллельными процессами.

Cleanup должен работать:

- при нормальном завершении;
- при ошибке;
- при получении поддерживаемых сигналов.

Не менять рабочие постоянные пути установки.

### Критерии приёмки

- в production shell-коде не остаётся временных путей, построенных только на `$$`;
- тесты или shell contract tests проверяют отсутствие таких конструкций;
- временные каталоги имеют безопасный режим доступа;
- cleanup не удаляет путь, который не был создан текущим процессом;
- параллельные запуски не используют один и тот же путь.

## Задача 3. Signal-safe восстановление Modbus payload

### Проблема

При установке или обновлении Modbus payload старый runtime/profile сохраняется во временном каталоге.

Текущий trap удаляет backup при `HUP`, `INT` или `TERM`, но восстановление старого payload выполняется только в обычной ветке ошибки.

Сигнал во время операции способен удалить backup до восстановления и оставить систему с неполным payload.

### Требуемый результат

При `HUP`, `INT` и `TERM`:

- старый Modbus runtime и profile должны быть восстановлены, если новая операция ещё не была успешно зафиксирована;
- cleanup должен выполняться только после попытки восстановления;
- исходный signal exit status должен быть сохранён;
- обычный успешный путь не должен откатывать уже завершённую установку;
- повторный cleanup должен быть безопасным;
- trap не должен рекурсивно вызывать сам себя.

### Критерии приёмки

Добавить тесты, моделирующие сигнал:

- после создания backup;
- после частичной замены payload;
- до commit нового payload.

Проверить:

- старые файлы восстановлены;
- временные файлы удалены;
- exit code соответствует сигналу;
- успешная установка не откатывается.

## Задача 4. Корректная миграция Modbus-конфигурации

### Проблема

Команда или режим `migrate-defaults` читает только базовые MDV-поля и игнорирует Modbus-параметры.

Из-за значений по умолчанию Modbus bus может быть мигрирован как MDV.

### Требуемый результат

При миграции существующего environment необходимо сохранять:

- protocol;
- profile;
- baud rate;
- data bits;
- parity;
- stop bits;
- port;
- addresses;
- bus id и остальные существующие значимые поля.

Поведение миграции чистого MDV должно остаться совместимым.

Некорректная или неполная Modbus-конфигурация должна приводить к понятной ошибке, а не к молчаливому переключению на MDV.

### Критерии приёмки

Тесты должны покрывать:

- миграцию MDV;
- миграцию Modbus со всеми serial-параметрами;
- разные значения parity и stop bits;
- отсутствие обязательного Modbus profile;
- отсутствие protocol в старом MDV-файле;
- round-trip сохранение семантически значимых значений.

## Задача 5. Пустой retained payload в web-клиенте

### Проблема

Общий JSON parser web-клиента безусловно вызывает `JSON.parse(payload)`.

Пустой retained payload в MQTT означает удаление retained-сообщения, но сейчас интерпретируется как повреждённый JSON.

Это относится к management JSON topics, включая конфигурацию, статусы, результаты, discovery, dashboard и schedules.

### Требуемый результат

Для каждого JSON topic определить явное поведение при пустом retained payload.

Пустой retained payload должен:

- считаться удалением retained value;
- не создавать ошибку JSON parsing;
- сбрасывать соответствующее состояние модели предсказуемым способом;
- не сохранять устаревшее значение как актуальное;
- не ломать обработку обычного непустого JSON.

Не применять это правило бездумно к обычным числовым и строковым factual topics, если у них другой контракт.

### Критерии приёмки

Web unit tests должны покрывать пустой retained payload как минимум для:

- buses config;
- manager status;
- operation result;
- discovery status/result;
- dashboard config/status;
- schedules config/status.

Также проверить:

- пустой non-retained payload обрабатывается в соответствии с контрактом конкретного topic;
- реально некорректный непустой JSON продолжает считаться ошибкой.

## Задача 6. Защита discovery от устаревшего результата

### Проблема

Discovery task хранит только bus id, port, worker и результат.

Если во время discovery изменились конфигурация, порт, protocol или profile, старый результат может быть опубликован как актуальный.

Предыдущий retained discovery result также не очищается в момент начала нового discovery.

### Требуемый результат

Discovery task должен быть связан со снимком конфигурации на момент старта.

Минимально нужно коррелировать результат с:

- revision конфигурации;
- bus id;
- port;
- protocol;
- profile или другим profile fingerprint;
- значимыми serial-настройками, если они влияют на discovery.

В момент начала нового discovery:

- старый retained result должен перестать считаться актуальным;
- status должен явно перейти в `running`.

При завершении:

- результат публикуется только если текущая конфигурация всё ещё соответствует снимку задачи;
- устаревший completion отбрасывается;
- пользователю публикуется понятный статус о том, что результат устарел или отменён;
- сервис не должен возобновлять работу по устаревшим предположениям.

### Критерии приёмки

Тесты:

- port изменён во время discovery;
- protocol изменён;
- Modbus profile изменён;
- bus удалён;
- revision изменилась без изменения bus fingerprint;
- старый retained result очищается или инвалидируется при старте;
- completion старой задачи не перезаписывает новый результат.

## Задача 7. Корреляция сохранения конфигурации в web

### Проблема

Web-клиент хранит только признак `pendingApply`.

Любое сообщение на `/mdvwb/config` во время pending может очистить состояние ожидания, включая старую retained-конфигурацию после reconnect.

Такой retained replay не является подтверждением конкретного save request.

### Требуемый результат

При отправке конфигурации web-клиент должен сохранять идентичность ожидаемой операции.

Допустимые способы корреляции:

- request id;
- ожидаемая revision;
- canonical payload;
- сочетание этих признаков.

Pending save должен завершаться только при получении ответа, который однозначно относится к отправленной операции.

Старый retained config:

- может обновить базовое состояние;
- не должен считаться подтверждением текущего save;
- не должен молча стирать пользовательский pending/dirty state.

Использовать metadata `retained`, доступную MQTT-клиенту, где это необходимо.

### Критерии приёмки

Тесты:

- retained old config приходит после отправки save;
- unrelated config update приходит во время pending;
- успешный result и matching config подтверждают save;
- rejected result очищает pending, но сохраняет редактируемый draft;
- reconnect не создаёт ложного успеха;
- повторная отправка после revision conflict работает предсказуемо.

## Задача 8. Только свежее factual state после reconnect

### Проблема

После разрыва MQTT-соединения web-приложение сохраняет старое factual state.

После reconnect retained replay может немедленно сделать controls доступными, хотя фактическое состояние текущей MQTT-сессии ещё не подтверждено.

### Требуемый результат

При disconnect factual state должно инвалидироваться.

После reconnect команды должны быть запрещены, пока не получен свежий текущесессионный factual snapshot.

Нужно различать:

- сохранённую конфигурацию и metadata;
- retained historical replay;
- подтверждённое factual state текущей сессии.

Простого условия `connected && state && !offline` недостаточно.

Решение может использовать session epoch, freshness marker, timestamps, online transition или другой надёжный контракт.

### Критерии приёмки

Тесты:

- controls отключаются сразу при disconnect;
- старое локальное состояние не разрешает команды;
- retained replay сам по себе не считается достаточной свежестью;
- после получения свежего snapshot controls снова доступны;
- состояние одного устройства не делает свежими остальные;
- group actions и schedules также не используют устаревшие факты.

## Задача 9. Общий capability contract для MDV и Modbus

### Проблема

Modbus profile capabilities существуют на уровне profile catalog/UI, но общий runtime и MQTT-контракт продолжают предполагать статический набор controls.

Нет единой нормализованной модели возможностей устройства.

### Требуемый результат

Создать общий capability contract, одинаково применимый к MDV и Modbus.

Для каждого semantic control контракт должен уметь описывать:

- supported;
- readable;
- writable;
- value type;
- допустимый range;
- enum values;
- дополнительную metadata, необходимую существующему UI/MQTT.

Capability contract должен:

- быть доступен runtime и MQTT-слою;
- поддерживать MDV без регрессии;
- строиться из Modbus profile;
- не дублировать несовместимые списки controls в разных подсистемах;
- иметь стабильную нормализованную семантику.

### Критерии приёмки

Тесты должны сравнивать capabilities:

- типичного MDV-устройства;
- полного Modbus profile;
- Modbus profile с отсутствующими controls;
- read-only control;
- write-only control, если такой контракт допустим;
- enum и numeric range.

## Задача 10. Принудительное соблюдение capabilities

### Проблема

Даже при наличии profile capabilities:

- MQTT metadata может рекламировать неподдерживаемые controls;
- command router принимает статический набор команд;
- group commands и schedules могут отправлять неподдерживаемые операции;
- web показывает controls, которых устройство не имеет.

### Требуемый результат

Capability contract из задачи 9 должен реально применяться во всех слоях.

Необходимо обеспечить:

- MQTT command router отклоняет unsupported или non-writable control;
- factual publisher не публикует выдуманные unsupported значения;
- metadata отражает реальные возможности;
- individual commands проверяют capability;
- group commands применяются только к совместимым целям и явно сообщают частичный/полный отказ;
- schedules валидируются против capabilities;
- web скрывает либо отключает недоступные controls;
- UI корректно показывает read-only controls;
- range и enum используются для валидации.

### Критерии приёмки

Интеграционные тесты минимум для:

- отсутствующего Power;
- read-only SetTemperature;
- ограниченного FanSpeed enum;
- отсутствующих Blinds;
- смешанной группы MDV и Modbus;
- schedule с unsupported action;
- отрицательного MQTT command без физической операции.

## Задача 11. Очистка retained topics по capabilities

### Проблема

При смене protocol или profile старые retained factual и metadata topics могут остаться в broker.

Новый runtime не публикует неподдерживаемый control, но старое retained значение продолжает отображаться как существующее.

### Требуемый результат

При изменении protocol/profile/capabilities необходимо удалить retained topics, которые больше не поддерживаются.

Очистка должна охватывать:

- factual control topics;
- command-related retained aliases, если они существуют;
- control metadata;
- device metadata, ставшую недействительной.

Очистка должна быть capability-based, а не только основанной на статическом полном списке controls.

Задача зависит от корректной обработки пустого retained payload в web из задачи 5.

### Критерии приёмки

Тесты:

- MDV → урезанный Modbus profile;
- Modbus profile A → profile B;
- Modbus → MDV;
- control остаётся поддерживаемым и не очищается;
- unsupported control очищается полностью вместе с metadata;
- web после retained deletion убирает control без JSON error.

## Задача 12. Удаление функции «использовать найденные адреса»

### Проблема

В web-интерфейсе присутствует кнопка и helper, автоматически заменяющие configured addresses результатом discovery.

Эта функция должна быть удалена как продуктовая возможность.

### Требуемый результат

Удалить:

- кнопку из UI;
- click handler;
- метод `useDiscoveredAddresses`;
- helper `configurationWithDiscoveryAddresses`;
- связанный state;
- связанные тесты и тексты;
- неиспользуемые импорты.

При этом сам discovery должен остаться:

- запуск discovery;
- status;
- отображение результата;
- ручное принятие решения пользователем без автоматической перезаписи конфигурации.

### Критерии приёмки

- поиск по проекту не находит удалённые identifiers;
- UI не показывает кнопку;
- discovery по-прежнему работает;
- тесты подтверждают отсутствие автоматического изменения addresses.

## Задача 13. Backup фактического web root

### Проблема

Установка и удаление поддерживают пользовательский `MDVWB_WWW_ROOT`, а backup hardcodes стандартные пути `var/www/mdvwb` и `var/www/fancoils`.

При нестандартном web root backup не содержит фактически установленный web.

### Требуемый результат

Backup должен:

- определить реальный используемый web root;
- сохранить это значение в backup metadata;
- архивировать именно этот путь;
- восстановить в тот же путь;
- корректно работать со стандартным значением;
- корректно обрабатывать отсутствие web root.

Не допускать path traversal через значение конфигурации.

### Критерии приёмки

Тесты:

- стандартный web root;
- пользовательский абсолютный web root;
- путь с пробелами;
- отсутствующий root;
- backup/restore round-trip;
- metadata содержит фактическое значение.

## Задача 14. Безопасный выбор последнего backup

### Проблема

Последний backup выбирается через конструкцию вида:

```sh
for candidate in $(ls ...)
```

Она ломает имена с пробелами, табами, переводами строк и другими специальными символами.

### Требуемый результат

Убрать parsing вывода `ls`.

Последний backup должен выбираться средствами, безопасными для любых допустимых имён файлов и каталогов.

Требуется:

- корректная сортировка по определённому критерию;
- отсутствие word splitting;
- корректное поведение при пустом каталоге;
- понятная ошибка, если backup отсутствует;
- отсутствие исполнения или интерпретации имени как shell-кода.

### Критерии приёмки

Тесты с именами:

- содержащими пробелы;
- содержащими `[` и `]`;
- начинающимися с `-`;
- с несколькими подходящими backup;
- с пустым backup root.

## Задача 15. Настоящий `--dry-run` для source installer

### Проблема

`deploy/install-from-source.sh --dry-run` до передачи управления основному installer уже выполняет изменяющие или дорогостоящие действия:

- apt update/install;
- configure/build;
- CTest;
- staging;
- потенциальные изменения controller.

### Требуемый результат

`--dry-run` должен быть действительно неразрушающим.

В dry-run запрещены:

- apt update;
- установка пакетов;
- configure/build;
- CTest;
- создание production staging;
- изменение systemd;
- изменение MQTT;
- изменение controller filesystem;
- запуск install/remove действий.

Dry-run должен:

- проверить аргументы;
- проверить очевидные preconditions без изменения системы;
- вывести точный план действий;
- завершиться предсказуемым кодом.

### Критерии приёмки

Contract tests должны подменять внешние команды и доказывать, что в dry-run не вызываются изменяющие операции.

Обычный режим установки должен продолжать выполнять полный pipeline.

## Задача 16. Честный source manifest

### Проблема

Source package manifest записывает только `git rev-parse HEAD`.

Если рабочее дерево грязное, содержимое пакета не соответствует указанному commit SHA.

### Требуемый результат

Выбран строгий контракт:

- source installer/package builder обязан отклонять dirty working tree;
- manifest SHA всегда должен точно описывать упакованный исходный код;
- untracked и modified файлы должны учитываться;
- диагностическое сообщение должно перечислять причину отказа;
- clean tree должен продолжать работать.

Не использовать скрывающий проблему суффикс без строгого определения содержимого. Требуется именно отказ от упаковки dirty tree.

### Критерии приёмки

Тесты:

- clean tracked tree;
- modified tracked file;
- staged change;
- untracked file;
- ignored build artifacts не должны считаться source modification, если они действительно ignored;
- manifest SHA совпадает с `HEAD`.

## Задача 17. Полный production package verifier

### Проблема

Verifier принимает неполный пакет, в котором могут отсутствовать обязательные production-компоненты.

Известные пропуски:

- `mdvwb-modbus`;
- production Modbus profile;
- `www/mdvwb/modbus-profile-ui.js`;
- другие web/transitive modules.

Также существует старый неполный package format 1, который может пройти production validation.

### Требуемый результат

Production verifier должен требовать полный runnable package.

Минимально проверить наличие и согласованность:

- основного MDV binary;
- `mdvwb-modbus`;
- manager;
- scheduler;
- offline helper;
- runtime launcher;
- systemd units;
- environment template;
- production Modbus profiles, включая `vrf_add_controller`;
- manager web;
- fancoils web;
- все прямые и транзитивные JS modules, импортируемые production entry points;
- install/upgrade/remove scripts;
- manifest и package version contract.

Неполный package format 1 должен быть:

- исключён из production validation;
- либо явно помещён в отдельный legacy/test-only путь, который нельзя спутать с production package.

Verifier должен выдавать конкретный список отсутствующих или несовместимых файлов.

### Критерии приёмки

Тесты должны отклонять пакет, из которого по одному удалены:

- `mdvwb-modbus`;
- production profile;
- `modbus-profile-ui.js`;
- любой обязательный transitive module;
- runtime launcher;
- systemd unit.

Полный package должен проходить проверку.

# 5. Порядок выполнения и зависимости

Задачи выполнять строго в указанном порядке.

Причины порядка:

- задачи 1–4 устраняют наибольшие риски повреждения системы и данных;
- задача 5 нужна до capability-based retained cleanup;
- задача 6 стабилизирует discovery до удаления связанной UI-функции;
- задачи 7–8 исправляют достоверность MQTT/web-состояния;
- задачи 9–11 последовательно вводят capability contract, enforcement и cleanup;
- задача 12 удаляет продуктовую функцию после стабилизации discovery;
- задачи 13–17 относятся к backup, installer и release pipeline;
- verifier завершается последним, когда окончательный состав production package уже определён.

Не объединять несколько задач в один большой неподконтрольный change set.

Допускается изменить общий helper заранее только тогда, когда это непосредственно требуется текущей задачей и не реализует будущую задачу скрытым образом.
