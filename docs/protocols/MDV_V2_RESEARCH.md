# MDV_v2 — исследование протокола и текущее состояние знаний

> **Статус:** исследование отложено до получения дополнительных данных по D0-ответам семискоростных кондиционеров.  
> **Назначение файла:** передать другому ИИ или разработчику все подтверждённые сведения, проектные решения и открытые вопросы без необходимости восстанавливать контекст по старому коду и заметкам.  
> **Критическое правило:** не реализовывать неизвестные части протокола по догадкам. Особенно это относится к отображению 7 физических скоростей в D0-ответе.

---

## 1. Терминология

В проекте используются два варианта протокола:

- `MDV_v1` — текущий протокол, уже реализованный в MDVWB.
- `MDV_v2` — рабочее название нового варианта протокола, исследуемого в этом документе.

`MDV_v2` — это внутреннее название проекта. Оно не обязательно является официальным названием производителя.

По архитектурному замыслу выбор версии протокола должен выполняться **на уровне шины**, например:

```json
{
  "id": 1,
  "protocol": "MDV_v2"
}
```

MQTT-топики и общая семантика приложения должны по возможности оставаться одинаковыми для `MDV_v1` и `MDV_v2`.

---

## 2. Уровни достоверности

В этом документе используются следующие метки:

- **ПОДТВЕРЖДЕНО** — наблюдалось в реальных дампах и/или независимо повторяется в нескольких реализациях.
- **РЕШЕНИЕ ПРОЕКТА** — это не свойство протокола, а выбранное поведение MDVWB.
- **НЕИЗВЕСТНО** — данных недостаточно.
- **НЕ РЕАЛИЗОВЫВАТЬ ПО ПРЕДПОЛОЖЕНИЮ** — существовали гипотезы, но подтверждения нет.

---

# 3. Физический интерфейс

## ПОДТВЕРЖДЕНО

Используется RS-485:

```text
Baud rate: 4800
Data bits: 8
Parity: None
Stop bits: 1
```

Перед основным кадром при передаче присутствует транспортный байт:

```text
FE
```

Сам протокольный кадр начинается с:

```text
AA
```

и заканчивается:

```text
55
```

---

# 4. Формат запросов

Передаваемый буфер вместе с транспортным `FE` имеет 17 байт.

Если убрать `FE`, внутренний протокольный кадр имеет 16 байт:

```text
[0]  AA
...
[14] checksum
[15] 55
```

---

# 5. Контрольная сумма запросов

## ПОДТВЕРЖДЕНО

Для передаваемого 17-байтного буфера:

```text
[0]  = FE
[1]  = AA
...
[14] = служебный байт
[15] = checksum
[16] = 55
```

контрольная сумма рассчитывается так:

```text
sum = 0x55 + byte[1] + byte[2] + ... + byte[14]
checksum = 0xFF - (sum mod 256)
```

То есть `FE` в расчёт не входит.

Для внутреннего 16-байтного кадра без `FE` это эквивалентно:

```text
sum = 0x55 + frame[0] + frame[1] + ... + frame[13]
frame[14] = 0xFF - (sum mod 256)
frame[15] = 0x55
```

---

# 6. Команда чтения состояния D0

## ПОДТВЕРЖДЕНО

Команда чтения в `MDV_v2`:

```text
D0
```

Передаваемый кадр:

```text
FE AA D0 ADDR 00 80 80 00 00 00 00 00 00 00 2F CRC 55
```

Где:

| TX index | Значение | Назначение |
|---:|---:|---|
| 0 | `FE` | транспортный префикс |
| 1 | `AA` | начало кадра |
| 2 | `D0` | команда чтения |
| 3 | `ADDR` | адрес фанкойла |
| 4 | `00` | фиксировано |
| 5 | `80` | фиксировано |
| 6 | `80` | фиксировано |
| 7–13 | `00` | фиксировано |
| 14 | `2F` | служебное дополнение к `D0` |
| 15 | `CRC` | контрольная сумма |
| 16 | `55` | конец кадра |

---

# 7. Команда записи состояния C3

## ПОДТВЕРЖДЕНО

Основная команда управления:

```text
C3
```

Формат:

```text
FE AA C3 ADDR 00 80 80 MODE_SPEED SPEED SET_TEMP 00 00 00 40 3C CRC 55
```

Более точно:

| TX index | Внутренний frame index без `FE` | Назначение |
|---:|---:|---|
| 0 | — | `FE`, транспортный префикс |
| 1 | 0 | `AA` |
| 2 | 1 | `C3` |
| 3 | 2 | адрес |
| 4 | 3 | `00` |
| 5 | 4 | `80` |
| 6 | 5 | `80` |
| 7 | 6 | Power + Mode |
| 8 | 7 | команда скорости |
| 9 | 8 | уставка температуры |
| 10 | 9 | `00` |
| 11 | 10 | `00` |
| 12 | 11 | `00` |
| 13 | 12 | `40` |
| 14 | 13 | `3C` |
| 15 | 14 | checksum |
| 16 | 15 | `55` |

# 8. Power и Mode

## ПОДТВЕРЖДЕНО

В C3 байт `TX[7]`, или `frame[6]` без `FE`, содержит питание и режим.

Наблюдавшиеся значения включённого устройства:

```text
0x81 = Fan
0x82 = Dry
0x84 = Heat
0x88 = Cool
```

Битовая структура:

```text
bit 7 = Power

bit 0 = Fan
bit 1 = Dry
bit 2 = Heat
bit 3 = Cool
```

То есть:

```text
0x80 + 0x01 = Fan ON
0x80 + 0x02 = Dry ON
0x80 + 0x04 = Heat ON
0x80 + 0x08 = Cool ON
```

---

## Автоматический режим нагрев/охлаждение

### РЕШЕНИЕ ПРОЕКТА

Для `MDV_v2` автоматический режим работы кондиционера **не поддерживать в MDVWB**.

Причина: исследованные кондиционеры этой версии не умеют нормально автоматически переключаться между нагревом и охлаждением.

В исследованиях встречалась экспериментальная команда:

```text
C4 ... 90 ...
```

но её не следует использовать как штатный `Auto Mode`.

### Для UI / MQTT

Для `MDV_v2` оставить режимы:

```text
Cool
Heat
Dry
Fan
```

и отдельный:

```text
Power = ON/OFF
```

Режим `Auto` для `MDV_v2` в интерфейсе не показывать.

---

## Важный нюанс OFF

### ПОДТВЕРЖДЕНО

В исследовательских C3-кадрах выключение встречалось как:

```text
Power/Mode byte = 0x00
```

При этом в D0-ответе выключенного устройства нижние биты режима могут сохраняться, например:

```text
0x08
```

то есть устройство выключено, но последний/текущий логический режим остаётся `Cool`.

### РЕШЕНИЕ ПРОЕКТА

На уровне приложения `Power` и `Mode` должны оставаться раздельными понятиями.

### НЕИЗВЕСТНО

Не подтверждено, следует ли при C3-выключении:

1. всегда отправлять `0x00`; или
2. только очищать bit 7 и сохранять mode bits.

Старые экспериментальные реализации использовали оба подхода.

Перед окончательной реализацией желательно подтвердить это на реальном оборудовании.

# 9. Уставка температуры

## ПОДТВЕРЖДЕНО

В C3:

```text
TX[9]
```

или:

```text
frame[8]
```

содержит уставку температуры напрямую.

Примеры:

```text
0x11 = 17 °C
0x12 = 18 °C
0x13 = 19 °C
0x14 = 20 °C
```

Не используется ни смещение, ни умножение.

# 10. Скорость вентилятора: C3-команда

## ПОДТВЕРЖДЕНО

У `MDV_v2` существуют как минимум:

- трёхскоростные кондиционеры;
- семискоростные кондиционеры;
- автоматическая скорость вентилятора.

Полная исследованная таблица C3 для семискоростной версии:

| Физическая скорость | Hex | Dec |
|---:|---:|---:|
| Auto | `0x80` | 128 |
| 1 | `0x0C` | 12 |
| 2 | `0x14` | 20 |
| 3 | `0x1A` | 26 |
| 4 | `0x22` | 34 |
| 5 | `0x29` | 41 |
| 6 | `0x31` | 49 |
| 7 | `0x39` | 57 |

Полные примеры:

```text
Auto:
FE AA C3 1B 00 80 80 00 80 11 00 00 00 40 3C 15 55

Speed 1:
FE AA C3 1B 00 80 80 00 0C 11 00 00 00 40 3C 89 55

Speed 2:
FE AA C3 1B 00 80 80 00 14 11 00 00 00 40 3C 81 55

Speed 3:
FE AA C3 1B 00 80 80 00 1A 11 00 00 00 40 3C 7B 55

Speed 4:
FE AA C3 1B 00 80 80 00 22 11 00 00 00 40 3C 73 55

Speed 5:
FE AA C3 1B 00 80 80 00 29 11 00 00 00 40 3C 6C 55

Speed 6:
FE AA C3 1B 00 80 80 00 31 11 00 00 00 40 3C 64 55

Speed 7:
FE AA C3 1B 00 80 80 00 39 11 00 00 00 40 3C 5C 55
```

---

# 11. Трёхскоростная версия

## ПОДТВЕРЖДЕНО

Для трёхскоростного устройства используются:

```text
Speed 1 = 0x0C
Speed 2 = 0x22
Speed 3 = 0x39
Auto    = 0x80
```

Это означает, что три стандартные скорости совпадают с уровнями:

```text
3-speed Low    = 7-speed level 1
3-speed Medium = 7-speed level 4
3-speed High   = 7-speed level 7
```

Схематично:

```text
7-speed:  1  2  3  4  5  6  7
          ^        ^        ^
3-speed: Low      Mid      High
```

Это подтверждено C3-командами, а не является предположением.

---

# 12. Решение MDVWB для управления скоростью

## РЕШЕНИЕ ПРОЕКТА

В пользовательском интерфейсе **не вводить 7 отдельных скоростей**.

Сохранить существующую логику:

```text
Speed 1 = Low
Speed 2 = Medium
Speed 3 = High
Speed 4 = Auto
```

Для команды C3 наиболее естественное соответствие:

```text
UI Low    -> native speed 1 -> 0x0C
UI Medium -> native speed 4 -> 0x22
UI High   -> native speed 7 -> 0x39
UI Auto   -> 0x80
```

Преимущество: одна и та же команда корректно соответствует известным кодам как 3-скоростного, так и 7-скоростного варианта.

---

# 13. D0-ответ: размер и общая структура

## ПОДТВЕРЖДЕНО

Ответ D0 имеет 32 протокольных байта от `AA` до `55`.

После выравнивания кадра:

```text
frame[0]  = AA
frame[1]  = D0
...
frame[30] = checksum
frame[31] = 55
```

В сырых последовательных данных после `55` может следовать `FE` следующего транспортного цикла. Этот `FE` не является частью 32-байтного D0-кадра.

---

# 14. Контрольная сумма D0-ответа

## ПОДТВЕРЖДЕНО ПО ЗАПИСАННЫМ КАДРАМ

Для 32-байтного ответа:

```text
sum = 0x55 + frame[0] + frame[1] + ... + frame[29]
frame[30] = 0xFF - (sum mod 256)
frame[31] = 0x55
```

Эта формула совпадает с наблюдавшимися реальными D0-кадрами.

---

# 15. Подтверждённые поля D0

## ПОДТВЕРЖДЕНО

Известны следующие позиции:

| Frame index | Назначение |
|---:|---|
| `[0]` | `AA` |
| `[1]` | команда `D0` |
| `[4]` | адрес устройства |
| `[7]` | статус / скорость вентилятора |
| `[8]` | SetTemp |
| `[9]` | RoomTemp raw |
| `[15]` | AlarmCode |
| `[21]` | Power + Mode |
| `[30]` | checksum |
| `[31]` | `55` |

Остальные байты пока не считать расшифрованными, даже если в старых исследованиях замечались корреляции.

# 16. D0 Power + Mode

## ПОДТВЕРЖДЕНО

Основной байт:

```text
frame[21]
```

Power:

```text
power = (frame[21] & 0x80) != 0
```

Mode:

```text
0x08 = Cool
0x04 = Heat
0x02 = Dry
0x01 = Fan
```

Рекомендуемый разбор:

```text
modeBits = frame[21] & 0x0F
```

Наблюдались, например:

```text
0x81 = Fan ON
0x82 = Dry ON
0x84 = Heat ON
0x88 = Cool ON
```

Также наблюдалось выключенное состояние:

```text
0x08 = Power OFF, режим Cool сохранён
```

# 17. D0 SetTemp

## ПОДТВЕРЖДЕНО

```text
SetTemp = frame[8]
```

Значение является температурой напрямую.

---

# 18. D0 RoomTemp

## ПОДТВЕРЖДЕНО

Сырая температура:

```text
raw = frame[9]
```

Формула:

```text
RoomTemp = (raw - 50) / 2.0
```

Примеры из реальных кадров:

```text
0x62 = 98 -> 24.0 °C
0x61 = 97 -> 23.5 °C
0x60 = 96 -> 23.0 °C
```

Важно сохранять половинные градусы.

---

# 19. D0 AlarmCode

## ПОДТВЕРЖДЕНО

```text
AlarmCode = frame[15]
```

Из старой реализации:

```text
0    -> аварии нет
!= 0 -> присутствует авария, код равен frame[15]
```

На уровне MQTT старой программы использовалась логика:

```text
Alarm = 0  -> нет аварии
Alarm = 1  -> авария устройства
Alarm = 2  -> нет связи
```

и:

```text
Status 0 = OFF
Status 1 = Cooling
Status 2 = Heating
Status 3 = Dry
Status 4 = Fan
Status 6 = Alarm
Status 7 = Offline
```

Режим Auto для `MDV_v2` в MDVWB использоваться не должен.

# 20. D0 скорость: подтверждённые сведения для 3-скоростной версии

## ПОДТВЕРЖДЕНО

Скорость находится в:

```text
frame[7]
```

Для известных трёх скоростей:

```text
0x02 = Low
0x04 = Medium
0x08 = High
```

Бит:

```text
0x80
```

означает автоматический режим скорости вентилятора.

Наблюдались комбинации:

```text
0x80 = Auto, активная ступень не указана известными битами
0x82 = Auto + фактически Low
0x84 = Auto + фактически Medium
0x88 = Auto + фактически High
```

Таким образом для 3-скоростной версии логично разделять:

```text
requested fan speed
active fan speed
```

Это хорошо соответствует существующей модели MDVWB:

```text
fanSpeed
activeFanSpeed
```

# 21. КРИТИЧЕСКИ НЕИЗВЕСТНО: D0 для 7 скоростей

## НЕИЗВЕСТНО

Нет реального семискоростного кондиционера, с которого можно снять D0-ответы для native speed 1..7.

Поэтому **неизвестно, как именно D0 кодирует семь физических скоростей**.

Не подтверждено ни одно из следующих предположений:

1. `frame[7]` продолжает сообщать только агрегированные Low / Medium / High.
2. `frame[7]` содержит новый код 1..7.
3. `frame[7]` использует комбинации битов для семи ступеней.
4. Точная native-скорость находится в другом байте D0.
5. В Auto точная активная скорость кодируется иначе, чем при ручной скорости.

### НЕ РЕАЛИЗОВЫВАТЬ ПО ПРЕДПОЛОЖЕНИЮ

Не создавать выдуманную таблицу D0 для speed 1..7.

Не считать, что C3-коды:

```text
0C 14 1A 22 29 31 39
```

обязательно повторяются в D0. Уже для трёхскоростной версии известно, что C3 и D0 используют разные кодировки.

# 22. Предполагаемая будущая нормализация 7 скоростей для UI

## РЕШЕНИЕ ПРОЕКТА, НО ТРЕБУЕТ ПОДТВЕРЖДЁННОГО D0

Если в будущем удастся достоверно получить native speed 1..7 из D0, пользовательский интерфейс всё равно должен оставить только 3 скорости + Auto.

Предполагаемая группировка для отображения:

```text
native 1,2   -> UI Low
native 3,4,5 -> UI Medium
native 6,7   -> UI High
native Auto  -> UI Auto
```

Это решение UI, а не утверждение о структуре D0.

# 23. Почему реализация MDV_v2 сейчас отложена

## РЕШЕНИЕ ПРОЕКТА

Протокол пока не внедрять в MDVWB.

Причина:

- C3-команды изучены достаточно хорошо.
- Основные поля D0 изучены достаточно хорошо.
- Но D0-отображение семи физических скоростей неизвестно.
- Угадывать протокол и затем строить вокруг догадки production-код нежелательно.

Сначала требуется исследовать семискоростной кондиционер, затем реализовать точную схему.

# 24. Что нужно снять с реального 7-скоростного кондиционера

Когда такое устройство станет доступно, желательно провести следующий эксперимент.

Зафиксировать:

```text
Power = ON
Mode = один и тот же
SetTemp = одна и та же
```

Последовательно установить:

```text
Speed 1
Speed 2
Speed 3
Speed 4
Speed 5
Speed 6
Speed 7
Auto
```

После стабилизации каждого режима сохранить **полный 32-байтный D0-ответ**, а не только `frame[7]`.

Нужно сравнивать все байты:

```text
frame[0] ... frame[31]
```

Особенно:

```text
frame[7]
```

но не ограничиваться им.

Для Auto желательно получить несколько кадров при разных фактических оборотах вентилятора.

Минимальный желательный набор:

```text
manual speed 1 -> D0
manual speed 2 -> D0
manual speed 3 -> D0
manual speed 4 -> D0
manual speed 5 -> D0
manual speed 6 -> D0
manual speed 7 -> D0

auto at low actual RPM    -> D0
auto at medium actual RPM -> D0
auto at high actual RPM   -> D0
```

# 27. Жалюзи / Blinds

## НЕИЗВЕСТНО

# 28. Lock / Unlock / Block

## НЕИЗВЕСТНО

Для `MDV_v1` в MDVWB существуют команды блокировки/разблокировки.

Для `MDV_v2` в текущем исследовании соответствующие кадры не подтверждены.

Не предполагать автоматически, что старые команды полностью совместимы.

---

# 29. Прочие D0-байты

## НЕИЗВЕСТНО

В D0 изменяются и другие байты, например в разных режимах и температурах.

Их назначение пока не зафиксировано с достаточной уверенностью.

До отдельного исследования не присваивать им семантику на основании единичных корреляций.

---

# 30. Архитектурное направление для будущей реализации

## РЕШЕНИЕ ПРОЕКТА

Когда исследование будет закончено, не копировать весь драйвер.

Предпочтительная структура:

```text
общий transport / frame collector / retry / MQTT
                 |
          protocol codec
            /       \
       MDV_v1      MDV_v2
```

Обе версии должны возвращать общую семантическую модель устройства.

Например:

```text
DeviceState
- power
- mode
- fanSpeed
- activeFanSpeed
- setTemperature
- roomTemperature
- alarm/errors
- ...
```

Версионные особенности должны находиться внутри codec.

---

# 31. Что должно остаться одинаковым снаружи

## РЕШЕНИЕ ПРОЕКТА

MQTT-топики желательно не менять.

Внешняя логика:

```text
Power:
0 / 1

Mode:
Cool
Heat
Dry
Fan
```

Для `MDV_v1` дополнительно может существовать:

```text
Auto
```

Для `MDV_v2` `Auto Mode` не показывать.

Speed:

```text
1 = Low
2 = Medium
3 = High
4 = Auto
```

даже если физически устройство имеет 7 ручных ступеней.

# 32. Возможные capabilities протокола

Будущая архитектура может использовать capability-описание, чтобы UI не проверял версию протокола напрямую.

Концептуально:

```cpp
struct ProtocolCapabilities {
    bool autoMode;
    bool autoFanSpeed;
    bool blinds;
    bool block;
};
```

Предварительно:

```text
MDV_v1:
autoMode     = true
autoFanSpeed = true
blinds       = true
block        = true

MDV_v2:
autoMode     = false
autoFanSpeed = true
blinds       = unknown
block        = unknown
```

Значения `unknown` нельзя без исследования превращать в `true`.

# 35. Инструкция следующему ИИ / разработчику

Если этот файл передан новому ИИ, соблюдать следующий порядок:

1. **Не начинать реализацию MDV_v2 с догадок о D0 7-speed.**
2. Считать C3-таблицу скоростей 1..7 подтверждённой.
3. Не переносить C3-коды скоростей напрямую в D0 decoder.
4. Считать подтверждёнными D0-поля `[4]`, `[7]`, `[8]`, `[9]`, `[15]`, `[21]`, `[30]`, `[31]` только в описанном выше объёме.
5. Не добавлять `Auto Mode` для MDV_v2.
6. Не удалять отдельный `Power` из общей модели MDVWB.
7. Не выводить 7 скоростей в пользовательский UI.
8. Когда появятся D0-кадры семискоростного устройства, сначала сравнить все 32 байта для скоростей 1..7 и Auto.
9. После подтверждения D0 обновить этот документ.
10. Только затем реализовывать production codec `MDV_v2`.
